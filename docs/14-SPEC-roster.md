# 14 · SPEC · Roster —— 可以变成的那些身体

> 取代旧的 `docs/12-SPEC-themes.md` §2 的主题表。§3（anchor 一致性）、§5（选择页）仍然有效。

## 1. 三种 kind

| kind | 是什么 | 版权性质 |
|---|---|---|
| `archetype` | 机器人物种。过去二十年真正形成了视觉 archetype 的那些形态 | 设计语言取材 —— 正当，和所有工业设计一样 |
| `guest` | 嘉宾：现实世界可辨认的人物客串 | **他人肖像** |
| `character` | 角色：虚构形象 | 原创的是我们的；现成 IP 是**他人著作权** |

分 kind 不是为了分类学好看，是因为这三者的**法律性质完全不同**，
混在一个数组里迟早会在某个深夜被不小心部署出去。

## 2. `clearance` 门

| 值 | 含义 | 进公开构建？ |
|---|---|---|
| `own` | 我们自己的造型 | ✅ |
| `licensed` | 已取得授权，`note` 写来源 | ✅ |
| `public-figure` | 真实在世人物的可辨认形象 | ❌ 默认不进 |
| `third-party-ip` | 他人角色 IP | ❌ 默认不进 |

机制是通的：任何条目填上 `look`、或往 `assets/refs/<id>/` 放参考图，就能生成、能选、能穿。
门只管**打包进公开构建的那一刻**。改 clearance 是一个创作+法务决定，不是一个技术决定。

> 现状：`archetype` 18 个 + `character` 4 个全部是 `own`，可以公开。
> `guest.founder` 是一个**空位**（没有 `look`），它在那里是为了说明这个位置想要什么，不是一份名单。

## 3. `coverage`：让"再加一个物种"变便宜

| | 生成哪些槽位 | 件数 | 成本 |
|---|---|---|---|
| `full` | 全部 10 个 × 2 变体 | 20 | 10 credits |
| `light` | 6 个标志性槽位（spine/head/upperArm/shin/foot/joint）× 1 变体 | 6 | 3 credits |

`light` 条目缺的槽位沿 `base` 链向上借（`genome.ts` 的 `baseChain`）。

**为什么要有这个分级**：物种的**数量本身**就是这件作品的内容 ——
观众滑过二十个身体时感受到的"寒武纪大爆发"，比任何单个身体做得多精致都重要。
所以加一个物种的边际成本必须低。

## 4. 形态空间

每个条目有两个 0..1 坐标：

```
                     life-like ↑
              毛球 ●   宠物 ●        ● 团子
        桌宠 ●                  ● 小怪物
                        ● 珊瑚      ● 异形
   球 ●                                    ● 穿衣的
        轮足 ●      鸟腿 ●         ● 运动员  ● 偶像
   无人车 ●                              ● 小人  ● 瓷
        移动机械臂 ●                          ● 工业
                                              → human-like
```

这不只是装饰：**开场轮播按这张图排布**，观众滑动时是在穿越形态空间而不是翻列表。
它也是我们自己的地图 —— 哪一片是空的，下一个该加什么，一眼看得出来。

## 5. 素材策展：好的素材显式保留

`assets/parts/curation.json`，跟部件文件一起进版本库。**它是人的判断，是这个项目里最不该丢的东西。**

| verdict | 效果 |
|---|---|
| `keep` | **永不重新生成**，即使 recipe / prompt 变了。它已经是资产，不再是配方的产物 |
| `reject` | 不进 genome 候选池，但**文件不删** —— 判断可能会变 |
| 未评级 | 正常参与。不评级不是错误，是默认状态 |

怎么评：开 `/dev/parts.html`，点部件循环 未评 → keep → reject → 未评，外框绿/红/灰。
或者 `npm run factory:curate -- --id=<partId> --verdict=keep`。

> 这条规则的存在理由：不显式保留，一次 prompt 微调就会把好东西悄悄重新生成掉，
> 而且你不会立刻发现 —— 等发现时已经找不回来了。
